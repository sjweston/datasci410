A real analysis: Start to finish

Let’s analyze a real dataset together — the General Social Survey, included in forcats as gss_cat.

Research question: Does age predict daily TV viewing among Americans — and does it differ by political party?

I’ll demonstrate the full workflow:

  1. Import and explore a real dataset
  2. Clean and recode categories
  3. Look at distributions (univariate & by group)
  4. Quantify the relationship (correlation + regression)
  5. Reshape with pivots and joins
  6. Build a Quarto report

This live demo is the heart of the lecture (~25-30 minutes). The dataset is real, public, and built into tidyverse – no download, no install. The research question is deliberately ordinary: it’s the kind of question a psych undergrad could answer for a class paper. Always check the levels of a categorical variable before recoding it. Students often assume the values they expect; the data has 10 levels including ‘No answer’, ‘Don’t know’, and ‘Other party’. Point out that ‘Ind,near rep’ and ‘Ind,near dem’ are leaners – we’ll group them with Independents in the next step. Step 2: Clean the data

gss_clean <- gss_cat |>
  drop_na(tvhours, age) |>
  mutate(
    party = case_when(
      partyid %in% c("Strong republican", "Not str republican") ~ "Republican",
      partyid %in% c("Strong democrat", "Not str democrat")     ~ "Democrat",
      partyid %in% c("Ind,near rep", "Independent", "Ind,near dem") ~ "Independent",
      TRUE ~ NA_character_
    ),
    party = factor(party, levels = c("Democrat", "Independent", "Republican"))
  ) |>
  drop_na(party)

Walk through each cleaning decision. “Why drop_na on tvhours and age?” Because we can’t analyze missing values. “Why collapse partyid into three categories?” Because the raw variable has 10 levels including ‘Don’t know’ and ‘No answer’ – too granular to plot. We’re treating ‘near rep’ and ‘near dem’ leaners as Independents for simplicity. Each of these decisions maps to a session: drop_na (Session 14), case_when (Session 4), factor levels (Session 12).

Step 7: Run a regression

A correlation gives one number. A regression gives a slope — how much does TV viewing change per year of age?

tv_model <- lm(tvhours ~ age + party, data = gss_clean)

library(broom)

Direct callback to Session 17. The lm() formula syntax (y ~ x1 + x2) is the foundation for almost all R modeling – t-tests, ANOVA, mixed models, even Bayesian models use the same notation. broom::tidy() turns the messy summary() output into a tidy tibble we can pipe and plot. Walk through the estimate column: the age slope tells us about how many additional minutes of TV per year of age.

glance(tv_model) |>

R² is tiny — age and party explain only a small slice of TV viewing. The story isn’t wrong, it just isn’t the whole story.

glance() gives one-row model summaries; tidy() gives one row per coefficient. Together they’re the broom workflow. The small R² is the right teaching moment: “statistically significant” ≠ “explains a lot.” Pair this with the earlier note about effect size. This also makes the case for multivariate models in PSY 420 – we’re not capturing the variables that really matter (income, education, screen-time substitution, etc.).

The inline R expressions (the backtick-r bits) are the magic. They evaluate at render time, so the numbers in the prose are pulled live from the data. No hand-typed numbers; no copy-paste from console output. If the data changes, the writeup updates automatically. Next slide shows what this renders to.

When things break

The 6 errors you’ll see most often (1/2)

Error What it means Fix
object 'x' not found Typo, wrong capitalization, or object not created yet Check spelling; run the code that creates it
could not find function Typo in function name or package not loaded Check spelling; run library()
unexpected symbol Missing |>, +, comma, or parenthesis Check the line before the error

Ask students: “Which of these have you gotten this quarter?” Hands will go up for all three. The most common is “object not found” (usually a capitalization issue or forgetting to run an earlier chunk). The “unexpected symbol” error is the trickiest because the actual problem is on the line before the error – emphasize checking the previous line.

The 6 errors you’ll see most often (2/2)

Error What it means Fix
non-numeric argument Math on text — variable is character, not numeric Check type with class() or glimpse()
did you mean '=='? Used = (assignment) instead of == (comparison) in filter() Change = to ==
ggplot + error Missing + between ggplot layers Every line except the last needs +

The bottom three are operator and syntax errors. The “did you mean ==” error is friendly – R is literally telling you the fix. The ggplot + error is a classic Session 2 issue that still trips students up; remind them ggplot uses + between layers, not |>.

A 5-step debugging strategy

  1. Read the error message — actually read it. It tells you where and what.
  1. Check the basics — package loaded? Object created? Spelling correct?
  1. Run line by line — pipe chains: run from the top, adding one line at a time. Which line breaks?
  1. Simplify — make a tiny test dataset (tibble(x = 1:3)) and try the same operation.
  1. Google it — include “R”, the package name, and the exact error message.

Step 3 (“run line by line”) is the most underused debugging technique among beginners. Demo it quickly: take a piped chain, highlight just the first line and run it, then add the next line, and so on. The line where it breaks is where the bug is. This is the single most useful debugging habit they can develop. Steps 1-3 solve ~90% of bugs.

When you ask for help: make a reprex

Reprex = reproducible example — the smallest code that recreates your error.

Bad: “My code doesn’t work. Help!”

Good:

“I’m trying to filter my data but getting ‘object not found’:

library(tidyverse)
data <- tibble(x = 1:3, y = c("a", "b", "c"))
filter(data, x > 1)
# Error: object 'data' not found

I expected rows where x > 1.”

Tip: Use dput() to share a small slice of your real data so others can recreate it exactly.

The reprex concept is a life skill for programming. Emphasize the contrast between the “bad” and “good” examples. The good example includes: the library call, a minimal dataset, the code that fails, and the expected vs. actual result. Even if students never post on Stack Overflow, learning to create a reprex forces them to isolate the problem – which often helps them solve it themselves.

Writing functions

Automate repetitive tasks:

# Instead of copying this code multiple times...
compute_scale_score <- function(data, items) {
  data |>
    rowwise() |>
    mutate(score = mean(c_across(all_of(items)), na.rm = TRUE)) |>
    ungroup()
}

# Use it anywhere
phq9_scored <- compute_scale_score(my_data, c("phq1", "phq2", "phq3"))

Interactive visualizations with Shiny

Build web apps for your data — no HTML or JavaScript required:

library(shiny)

ui <- fluidPage(
  selectInput("party", "Choose party:",
              choices = c("Democrat", "Independent", "Republican")),
  plotOutput("plot")
)

server <- function(input, output) {
  output$plot <- renderPlot({
    gss_clean |>
      filter(party == input$party) |>
      ggplot(aes(age, tvhours)) + geom_point()
  })
}

shinyApp(ui, server)

Don’t go deep on any of these – the point is to show that R has a thoughtful, well-built package for almost every task they’ll encounter. tidymodels is the natural next step for anyone interested in prediction or machine learning. ellmer is brand new and worth mentioning because LLM workflows are increasingly part of research.

Go deeper (cont.): communication & workflow

Communication:

  • gtsummary — publication-ready summary tables
  • quarto — websites, books, dashboards (you’ve used the basics)

Workflow:

  • targets — reproducible analysis pipelines
  • renv — project-level package management

gtsummary is the single biggest time-saver for anyone writing a thesis or paper – it produces APA-style descriptives in one call. targets and renv are about making analyses survive over time: targets caches expensive computations so you don’t re-run them, and renv pins your package versions so the analysis still works two years later. Final reflections

What makes a good data scientist?

It’s not about knowing every function or memorizing syntax.

Good data scientists:

  1. Ask good questions — what story is the data telling?
  2. Stay curious — always learning new tools and techniques
  3. Communicate clearly — make complex findings accessible
  4. Work reproducibly — others can verify and build on your work
  5. Think critically — question assumptions, check for bias
  6. Persist through errors — debugging is part of the job

You’ve developed all of these skills this quarter.

This is the emotional core of the closing section. Slow down here. Read through the six qualities and pause on each one. The last line – “You’ve developed all of these skills this quarter” – should land. Students often don’t realize how much they’ve grown because it happened gradually. Connecting each quality back to specific class moments makes it concrete: “Remember when you debugged your partner’s code? That’s persistence.”

The growth mindset

Ten weeks ago, many of you had never written a line of code.

Now you can:

  • Import and clean messy data
  • Create publication-quality visualizations
  • Wrangle complex datasets with joins and pivots
  • Handle missing data appropriately
  • Build reproducible reports

That’s incredible growth.

Let the bullet list build slowly. Each skill maps to a specific part of the course. Students may not feel like they “mastered” everything, and that’s fine – emphasize that they can do all of these things, even if they still need to look things up. Looking things up is what professionals do too. The phrase “That’s incredible growth” is genuine – let it land before moving on.

Errors are part of the process
